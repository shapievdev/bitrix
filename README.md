# Задачи+ — приложение для Битрикс24

Расширение функционала задач Битрикс24: собственные статусы, канбан-доски
и всё, что не помещается в штатную логику портала.

**Стек:** Laravel 13 · Vue 3 · Inertia · Tailwind 4 · PostgreSQL

---

## Как это устроено

Приложение живёт внутри iframe на портале Битрикс24. Портал сам открывает
его POST-запросом, передавая токены текущего сотрудника — своей формы входа
у приложения нет.

```
Битрикс24                                Приложение
─────────────────────────────────────────────────────────────────
установка          ──POST /bitrix/install──▶  InstallController
                                              сохраняет токены,
                                              подписывается на события
                   ◀──BX24.installFinish()──

                   ──POST /bitrix/event────▶  EventController
   (ONAPPINSTALL)                             приносит application_token

открытие в iframe  ──POST / ──────────────▶  EntryController
                                              проверяет AUTH_ID через
                                              user.current, заводит
                                              портал и пользователя
                   ◀──302 /app────────────

                   ──POST /bitrix/event────▶  EventController
   (ONTASKUPDATE)                             проверяет application_token
                                              → очередь
```

### Ключевые части

| Что | Где |
|---|---|
| Настройки приложения | `config/bitrix24.php` |
| REST-клиент | `app/Services/Bitrix24/Bitrix24Client.php` |
| Обновление токенов | `app/Services/Bitrix24/TokenManager.php` |
| Заведение порталов | `app/Services/Bitrix24/PortalRegistrar.php` |
| Контекст портала | `app/Support/PortalContext.php` |
| Точки входа | `app/Http/Controllers/Bitrix24/` |
| Обёртки над BX24.js | `resources/js/bitrix.js` |
| Канбан: перенос карточек | `app/Services/Kanban/CardMover.php` |
| Канбан: синхронизация | `app/Services/Kanban/TaskSynchronizer.php` |

### Мультитенантность

Приложение сейчас ставится на один портал, но схема с самого начала
рассчитана на много: ключ — `portals.member_id`, все доменные модели
подключают трейт `BelongsToPortal` и автоматически фильтруются по
текущему порталу. Переход на тиражное приложение не потребует
переписывания запросов.

```php
use App\Models\Concerns\BelongsToPortal;

class Board extends Model
{
    use BelongsToPortal; // portal_id проставится и отфильтруется сам
}
```

Без контекста запрос возвращает **пустоту** — исключений нет даже для
консоли. Послабление «в консоли не фильтруем» делало скоуп пустышкой во
всём наборе тестов, то есть ровно там, где утечку между порталами и надо
ловить. Поэтому в командах и очередях контекст задаётся явно:

```php
PortalContext::run($portal, fn () => Board::query()->get());
```

А осознанный обход всех порталов запрашивается вслух:

```php
Board::query()->acrossPortals()->get();
```

## Доски и карточки

```
Board ──┬── BoardColumn (свой статус, необязательно привязан к STATUS Битрикса)
        │        │
        │        └── TaskCard (задача портала: колонка + порядок — наши,
        │                      остальные поля — копия для отрисовки)
        │                 │
        └─────────────────┴── CardTransition (история переходов и время на этапе)
```

Источник истины по задачам остаётся на портале. Своё у приложения только
два поля: в какой колонке лежит карточка и в каком порядке. Поля задачи
копируются в `task_cards`, потому что доска на 200 карточек не может
дёргать REST на каждую отрисовку — лимит в 2 запроса в секунду это убьёт.

### Как статусы ходят в обе стороны

Двусторонняя синхронизация статусов легко зацикливается, поэтому правила
жёсткие:

- **Доска → Битрикс.** Перенос в колонку с `bitrix_status` шлёт
  `tasks.task.update`. Колонка без привязки (`Ревью`, `Заблокировано` —
  ровно то, ради чего приложение и делается) не шлёт ничего.
- **Битрикс → доска.** Карточка двигается, только если статус
  **сменился** с прошлой синхронизации. Сверять текущую колонку со
  статусом нельзя: карточка, уведённая в собственную колонку,
  возвращалась бы обратно при каждом обходе.
- Перемещение, вызванное событием портала, статус обратно не шлёт.

### Синхронизация

```bash
php artisan bitrix:sync-boards                    # все порталы, все доски
php artisan bitrix:sync-boards --portal=домен     # один портал
php artisan bitrix:sync-boards --board=3          # одна доска
```

События портала теряются: доставка не гарантирована, а если приложение
было недоступно, Битрикс перестаёт их слать совсем. Поэтому полный обход
висит в расписании (`routes/console.php`, раз в полчаса) — он и приводит
доски в согласованное состояние.

## Работа с REST

```php
use App\Facades\Bitrix24;

// От имени приложения — для фоновой синхронизации
$tasks = Bitrix24::forPortal($portal)->call('tasks.task.list', [
    'filter' => ['RESPONSIBLE_ID' => 1],
]);

// От имени сотрудника — когда важны его права и авторство
Bitrix24::forUser($user)->call('tasks.task.update', [
    'taskId' => 42,
    'fields' => ['TITLE' => 'Новое название'],
]);

// Текущий пользователь из iframe
Bitrix24::current()->call('user.current');
```

**Постраничный обход** — пагинация Битрикса скрыта в генераторе:

```php
foreach (Bitrix24::forPortal($portal)->list('tasks.task.list', [], 'tasks') as $task) {
    // ...
}
```

**Пачка запросов** — до 50 методов за один REST-вызов, основной способ
уложиться в лимиты:

```php
$result = Bitrix24::forPortal($portal)->batch([
    'user' => ['user.current', []],
    'tasks' => ['tasks.task.list', ['filter' => ['STATUS' => 2]]],
]);
```

Клиент сам обновляет протухшие токены, повторяет запросы при
`QUERY_LIMIT_EXCEEDED` и держит не больше 2 запросов в секунду на портал.

## Запуск

### 1. Зависимости и база

```bash
composer install
npm install
```

Создайте базу и пропишите доступы в `.env` (`DB_*`), затем:

```bash
php artisan migrate
```

### 2. HTTPS-туннель

Битрикс24 грузит приложение только по HTTPS, поэтому на разработке нужен
туннель:

```bash
ngrok http 8000          # или: cloudflared tunnel --url http://localhost:8000
```

Полученный адрес пропишите в `.env`:

```dotenv
APP_URL=https://ваш-туннель.ngrok-free.app
BITRIX24_FORCE_HTTPS=true
```

### 3. Приложение на портале

Битрикс24 → **Разработчикам** → **Другое** → **Локальное приложение**:

| Поле | Значение |
|---|---|
| Тип | Серверное (использует только API) |
| Путь обработчика | `https://ваш-туннель/` |
| Путь для первоначальной установки | `https://ваш-туннель/bitrix/install` |
| Права | Задачи, Пользователи, Встраивание (`task`, `user`, `placement`) |

Полученные `client_id` и `client_secret` — в `.env`:

```dotenv
BITRIX24_CLIENT_ID=local.xxxxxxxx
BITRIX24_CLIENT_SECRET=xxxxxxxx
BITRIX24_SCOPE=task,user,placement
```

Права в `.env` должны совпадать с выданными на портале — иначе REST вернёт
`INVALID_CREDENTIALS` при первом же вызове метода вне scope.

### 4. Запуск

```bash
php artisan serve
npm run dev
php artisan queue:work    # события портала обрабатываются в очереди
```

Откройте приложение из левого меню портала.

## Что важно помнить

**Сессия внутри iframe.** Приложение открывается на чужом домене, поэтому
cookie сессии выставлена с `SameSite=None; Secure` — без этого вход слетает
на каждом запросе. На случай, если браузер режет сторонние cookie, контекст
портала дублируется подписанным токеном в заголовке `X-Bitrix-Context`.

**Высота фрейма.** Битрикс задаёт iframe фиксированную высоту, своей полосы
прокрутки у него нет. После каждого перехода вызывается `BX24.fitWindow()`;
при изменениях без перехода (перетаскивание карточек) дёргайте `resizeFrame()`
из `resources/js/bitrix.js` вручную.

**Подлинность событий.** Адрес `/bitrix/event` публичный. Единственное, что
отличает настоящее событие от подделки, — `application_token`, который портал
присылает при установке. Не отключайте эту проверку.

**Токены портала и пользователя.** Токены из установки принадлежат
администратору и живут в `portals` — ими работают фоновые задачи. Токены из
iframe принадлежат открывшему сотруднику и живут в `portal_users` — ими
выполняются действия, где важны права и авторство.
